# Why a Delta managed table shows `Type: EXTERNAL` in `DESCRIBE TABLE EXTENDED`

## Summary

In this repo's Delta Lake + Spark + Hive Metastore setup (`docker-compose.yml`: `deltaio/delta-docker:4.3.1` + `apache/hive:4.0.0` + Postgres backing store), a Delta table created **without a `LOCATION`** (i.e. intended as a managed table) always shows `Type: EXTERNAL` in `DESCRIBE TABLE EXTENDED`. This is **not a display bug** — the table really is stored as `EXTERNAL_TABLE` in the Hive Metastore. Despite that, `DROP TABLE` still deletes the physical data exactly like a real managed table, thanks to a hidden flag (`external.table.purge`) that Spark never surfaces for Delta tables.

## Context / how to reproduce

```python
spark.sql("""
CREATE TABLE bai02.customers_sql (
    customer_id INT, full_name STRING, country STRING, signup_date DATE
)
USING DELTA
""")
spark.sql("DESCRIBE TABLE EXTENDED bai02.customers_sql").show(50, truncate=False)
```

Result:

```
Type       EXTERNAL
Location   s3a://data-platform/managed/bai02.db/customers_sql
Provider   delta
```

No `LOCATION` was given in the DDL — the path was auto-generated by the metastore under the warehouse dir (`spark.sql.warehouse.dir=s3a://data-platform/managed`), so it should logically be `MANAGED` — yet it shows `EXTERNAL`.

## Root cause: Hive "Strict Managed Tables"

Since Hive 3.x (the image here uses Hive 4.0.0), `TBL_TYPE = MANAGED_TABLE` is reserved **only** for ACID/transactional tables that Hive itself fully owns (Hive-native ORC + transaction manager). A non-Hive-native table like Delta (Parquet files + `_delta_log`) doesn't qualify for a genuine MANAGED type in the Hive Metastore.

When Spark/Delta requests a managed table (Delta itself computes `tableType = MANAGED` when no `LOCATION` is given — see `AbstractDeltaCatalog.scala` in [delta-io/delta](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/catalog/AbstractDeltaCatalog.scala#L292-L296)), the Hive Metastore **automatically translates** that request into:

- `TBL_TYPE = EXTERNAL_TABLE`
- plus `external.table.purge = TRUE` — tells the metastore: *"even though it's labeled EXTERNAL, still delete the data on DROP, just like a managed table"*
- and `TRANSLATED_TO_EXTERNAL = TRUE` — marks the table as auto-translated (as opposed to a genuine external table the user explicitly declared).

This is **intentional Hive behavior**, not a bug.

## Empirical evidence

Checked directly against the Postgres backing store of the Hive Metastore (`metastore-db` service):

```bash
docker exec metastore-db psql -U hive -d hive -c "
SELECT t.\"TBL_NAME\", p.\"PARAM_KEY\", p.\"PARAM_VALUE\"
FROM \"TBLS\" t
JOIN \"DBS\" d ON t.\"DB_ID\"=d.\"DB_ID\"
JOIN \"TABLE_PARAMS\" p ON p.\"TBL_ID\"=t.\"TBL_ID\"
WHERE d.\"NAME\"='bai02' AND t.\"TBL_NAME\"='customers_sql'
  AND (p.\"PARAM_KEY\" ILIKE '%external%' OR p.\"PARAM_KEY\" ILIKE '%purge%');"
```

Result — table created **without `LOCATION`** (`bai02.customers_sql`, `bai03.ordersx`):

| PARAM_KEY | PARAM_VALUE |
|---|---|
| `EXTERNAL` | `TRUE` |
| `external.table.purge` | `TRUE` |
| `TRANSLATED_TO_EXTERNAL` | `TRUE` |

Compared with a table created **with an explicit `LOCATION`** (`bai03.orders`, path `s3a://data-platform/external/orders`):

| PARAM_KEY | PARAM_VALUE |
|---|---|
| `EXTERNAL` | `TRUE` |
| `external.table.purge` | *(absent)* |
| `TRANSLATED_TO_EXTERNAL` | *(absent)* |

## Behavior comparison

| | No `LOCATION` (managed-intent) | With `LOCATION` (genuine external) |
|---|---|---|
| `TBL_TYPE` (Hive) | `EXTERNAL_TABLE` | `EXTERNAL_TABLE` |
| `DESCRIBE` shows `Type` | `EXTERNAL` | `EXTERNAL` |
| `external.table.purge` | `TRUE` | absent |
| `TRANSLATED_TO_EXTERNAL` | `TRUE` | absent |
| `DROP TABLE` deletes data? | **Yes** | **No** |

Conclusion: the `Type` column in `DESCRIBE TABLE EXTENDED` is **not enough** to know whether `DROP TABLE` will delete the data. You also need `external.table.purge`.

## Why Spark never shows `external.table.purge`

For a Delta table, the "Table Properties" line in `DESCRIBE`/`SHOW TBLPROPERTIES` comes from `DeltaTableV2.properties()` ([source](https://github.com/delta-io/delta/blob/v4.3.1/spark/src/main/scala/org/apache/spark/sql/delta/catalog/DeltaTableV2.scala#L241-L270)) — this function builds the displayed map **from scratch**, starting from `initialSnapshot.getProperties` (the metadata of the Delta transaction log itself, `_delta_log/...json`), then cherry-picks a handful of extra fields (`provider`, `location`, `owner`, cluster-by, comment). It **never** merges the raw `TABLE_PARAMS` from the Hive Metastore into that map.

In other words, Delta has two separate metadata layers:

1. **Delta transaction log** (`_delta_log`) — Delta's own source of truth; Spark displays this layer via `DESCRIBE`.
2. **Hive Metastore catalog bookkeeping** (`TBLS`, `TABLE_PARAMS`) — used for catalog integration (`EXTERNAL`, `external.table.purge`, `TRANSLATED_TO_EXTERNAL`, `numFiles`, `totalSize`, `spark.sql.*`, ...). This layer is **never** exposed through any Spark SQL command (`DESCRIBE`, `DESCRIBE FORMATTED`, `SHOW TBLPROPERTIES`, `SHOW CREATE TABLE`) for a Delta table.

The `hive-metastore` container in this repo only runs the bare `HiveMetaStore` service (thrift port 9083) — no HiveServer2 — so `beeline`/Hive CLI can't be used either to see the native Hive view.

## How to actually see `external.table.purge` / `TRANSLATED_TO_EXTERNAL`

### Option 1 — Query the Postgres backing store directly

```bash
docker exec metastore-db psql -U hive -d hive -c "
SELECT p.\"PARAM_KEY\", p.\"PARAM_VALUE\"
FROM \"TBLS\" t
JOIN \"DBS\" d ON t.\"DB_ID\"=d.\"DB_ID\"
JOIN \"TABLE_PARAMS\" p ON p.\"TBL_ID\"=t.\"TBL_ID\"
WHERE d.\"NAME\"='<db>' AND t.\"TBL_NAME\"='<table>'
ORDER BY p.\"PARAM_KEY\";"
```

### Option 2 — Call the Hive Metastore Thrift client directly from the notebook (no need to leave PySpark)

```python
from py4j.java_gateway import java_import

jvm = spark._jvm
java_import(jvm, "org.apache.hadoop.hive.conf.HiveConf")
java_import(jvm, "org.apache.hadoop.hive.metastore.HiveMetaStoreClient")

hconf = jvm.HiveConf()
hconf.set("hive.metastore.uris", "thrift://hive-metastore:9083")
client = jvm.HiveMetaStoreClient(hconf)

tbl = client.getTable("bai03", "ordersx")
print("TableType:", tbl.getTableType())
for k in tbl.getParameters().keySet():
    print(k, "=", tbl.getParameters().get(k))
```

The `HiveConf`/`HiveMetaStoreClient` classes are already on Spark's classpath (the `deltaio/delta-docker` image bundles the hive-metastore jar), so nothing extra needs to be installed.

## Practical takeaways

- Don't use the `Type` column in `DESCRIBE TABLE EXTENDED` to decide whether `DROP TABLE` is safe — with Delta on a strict-managed-tables Hive Metastore, `EXTERNAL` does not mean "data is preserved."
- To create a genuine external table (data survives `DROP TABLE`), you must specify an explicit `LOCATION` in `CREATE TABLE`.
- To be certain about a specific table's delete-on-drop behavior, check `external.table.purge` using one of the two methods above — never rely on any Spark `DESCRIBE`/`SHOW` command for this.
